# v4 Plan Gap Analysis

Source docs reviewed: `PLAN_v4.md`, `2026-04-09-13-34_v4-prompting-deep-dive.md`
Source code reviewed: `gpu_config.py`, `visual_capture.py`, `volume_info.py`, `molmo_glancer.py`

---

## Critical — Structural decisions the plan doesn't resolve

### G1. History structure for batched actions

The current code appends **one history entry per action** (`history.append({...})` in a 1:1 loop).
The deep-dive's §5.3 shows sub-views labelled `1a, 1b, 1c` within a single iteration — implying one
entry per iteration-batch, not one per view. The plan never makes this explicit.

Does a batch of 3 actions become:
- One history entry with a list of sub-findings, or
- Three separate history entries tagged to the same iteration?

This cascades into `format_structured_findings()`, history compression, `count_prior_matches()`,
and `fov_feedback` storage. **Needs a design decision before writing any `run_agent()` code.**

---

### G2. `validate_action()` not updated for batched format

The plan introduces `parse_action_batch()` but never mentions updating `validate_action()`.
Currently it handles a single action dict. In v4, each action in the `{"actions": [...]}` array
needs zoom resolution, coordinate clamping, and `_resolve_show()` — either via a loop call or a
new batch-aware wrapper.

---

### G3. Duplicate detection in batched mode

`count_prior_matches()` / `_action_fingerprint()` compare individual actions against history.
With batched planning the unit of comparison is ambiguous: fingerprint the whole batch, or each
individual action within it?

The consecutive-duplicate forcing logic (`max_consecutive_duplicates = 3`) also assumes
single-action iterations. How does this behave when OLMo plans a batch?

## Moderate — Easy to miss during implementation

### G4. `save_prompt_templates()` not mentioned (~140 lines, 1093–1234)

This function saves all prompt templates to `results/prompts.md` at agent startup. It needs
updating for: the new OLMo system prompt, the restructured action schema, the batched decision
prompt, and the new Molmo2 imaging context block. Could silently produce stale/wrong output
if skipped.

---

### G5. Imaging context block omitted from first-look (Phase 1)

§15.6 of the deep-dive says the imaging context block should be added to all Molmo2 interpret
prompts. But Phase 1 ("capture + interpret initial view") is described with no mention of it.
The first-look interpret call should get the imaging context block too.

---

### G6. OLMo token usage not wired up

`ask_text_olmo()` is defined in the checklist but its return format isn't specified. The current
`ask_text()` returns `(text, token_counts)` and this flows into `save_outputs()` →
`token_usage.json`. The plan doesn't say whether `ask_text_olmo()` returns the same tuple shape
or how its tokens accumulate into the session total.

---

### G7. Scan browser session reuse in batched Molmo phase

`execute_scan()` internally calls `create_browser()` each time — spinning up and tearing down a
full Playwright browser per scan. In v4's batched Molmo phase, OLMo can plan multiple scans per
batch. This was acceptable at 1 scan/iteration but could add meaningful overhead at 3–4
scans/batch. The plan doesn't address reuse or acknowledge the overhead.

---

## Minor — Low risk but worth noting

### G8. `count` action dispatch in the batched Molmo phase

The plan's Molmo phase says "for each planned action: capture + `ask_vision(Molmo2)`: interpret
→ finding." But `count` requires a multi-step inner loop: scan → per-keyframe
`ask_vision_pointing()` → `ask_text_olmo()` for interpretation. `count` is listed as a valid
batched visual action but its dispatch path in the Molmo phase is fundamentally different from
screenshot/scan.

---

### G9. `scan_count` / `screenshot_id` counters in batched mode

These global counters currently increment 1:1 per iteration. In a batched Molmo phase executing
3 screenshots, all three fire in the same iteration. The plan doesn't say whether counters
increment within the batch (correct) or whether any downstream logic assumes they match the
iteration number.

---

### G10. `crossSectionScale` availability for imaging context block

§15.6 computes `um_per_pixel = view_spec.get("crossSectionScale", ...)` for the imaging context
block. This field is written into the action by `validate_action()` via `resolve_zoom()`. The
imaging context block can only be built **after** validation runs — a dependency the plan doesn't
state explicitly.
