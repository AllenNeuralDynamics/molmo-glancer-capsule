### A3. Architecture diagram vs deep-dive §6 — plan vs reason call count

PLAN_v4.md architecture (lines 314-326) shows **3 phases per iteration:**
```
OLMo plan → Molmo capture → OLMo reason
```
This implies 2 OLMo text calls per iteration.

Deep-dive §6 (lines 384-388) says:
> "In v4, this reasoning is folded into the decision prompt... There is no
>  separate 'reasoning phase' call; instead, OLMo's <think> block handles
>  the synthesis before outputting the action."

This implies 1 OLMo call per iteration (combined reason + plan).

**Number of disk loads per iteration:** OLMo loads from disk (~30-60s) each time.
With 2 separate calls, there are 2 loads per iteration if OLMo is deleted between them.
With 1 folded call, there's 1 load per iteration.

**Recommendation:** The deep-dive's folded approach is better. Each iteration:
1. swap_to_olmo (load ~30-60s)
2. OLMo: reason about latest finding + plan next action (1 call)
3. swap_to_molmo (delete OLMo, move Molmo ~5s)
4. Molmo: capture + interpret

This gives 1 OLMo load per iteration instead of 2, halving the expensive swap
overhead. The architecture diagram in PLAN_v4.md should be updated to match.

**Note:** The swap count stays at 2 per iteration (swap_to_olmo + swap_to_molmo),
but the expensive direction (disk load) happens only once. The "2 swap cycles"
framing in the plan is technically correct for physical swaps but misleading about
the actual overhead.

## B. Code-level gaps not covered by the plan

### B1. `ask_text()` becomes dead code — not mentioned

All text calls move to `ask_text_olmo()` in v4. The existing `ask_text()` (which
uses Molmo2's 7B backbone via `processor.apply_chat_template()`) becomes unused.

The plan should state whether to:
- **Remove** `ask_text()` (cleaner, single code path)
- **Keep** it for debugging/fallback (adds complexity)

### B2. Count interpretation — structural change not explicit

In v3, count interpretation uses `ask_text()` during the Molmo phase.
In v4, this moves to OLMo (deep-dive §14 Q2 recommends it).

The structural change: count pointing (Molmo) produces raw statistics →
these become part of the "finding" → OLMo receives them in the next
reason+plan call and interprets them there.

PLAN_v4.md §2 mentions `ask_text_olmo()` but doesn't explicitly describe
the count dispatch path. Deep-dive §14 Q2 is still framed as an open question
with a recommendation, not a definitive decision.

**Recommendation:** Resolve Q2 as decided (route to OLMo) and note in PLAN_v4.md
§2 that count interpretation moves from the Molmo phase to the OLMo phase.

### B3. `run_agent()` signature change — config access unclear

Current: `run_agent(model, processor, config, ng_link, question)`
v4: `run_agent(manager, config, ng_link, question)` or `run_agent(manager, ...)`

Does `ModelManager` carry the config dict? If so, does `run_agent` also take
config separately? The plan lists `ModelManager` methods but doesn't show
whether config is a constructor parameter or separate.

### B4. Token tracking needs OLMo vs Molmo separation

`save_outputs()` writes `token_usage.json` with a single totals dict.
In v4, token usage should distinguish OLMo tokens from Molmo2 tokens —
useful for cost/latency analysis and debugging.

The plan doesn't mention this. Suggested: track `olmo_input_tokens`,
`olmo_output_tokens`, `molmo_input_tokens`, `molmo_output_tokens` separately.

### B5. Frame cache preservation

`run_agent()` uses a `frame_cache` dict (keyed by `_geometry_fingerprint()`)
to avoid re-capturing scans for the same region. This is important for count
actions that reuse scan geometry. The plan doesn't mention preserving this
optimization through the refactoring.

### B6. Video metadata — 0.5 FPS trick

`ask_scan()` uses `VideoMetadata(fps=0.5)` to prevent Molmo2's frame sampler
from dropping frames. This is a critical implementation detail that must survive
the refactoring. Not mentioned in any plan document.

### B7. Async scan execution — separate event loop

`execute_scan()` spawns `_run_sequential()` in a separate thread with its own
`asyncio.new_event_loop()` to avoid "event loop already running" conflicts.
This architectural detail must be preserved. Not mentioned in the plan.

## C. Minor / cosmetic issues

### C1. `_infer_layer_role()` duplicate pattern

Deep-dive §15.5, lines 940-944:
```python
if any(k in name for k in ("dapi", "hoechst", "nuc", "nuclei")):
    return "nuclear stain — bright spots = all cell nuclei"
...
if any(k in name for k in ("dapi", "blue")):
    return "nuclear stain channel"
```

"dapi" appears in both checks. The third check's "dapi" branch is unreachable
(caught by the first check). Only "blue" is unique to the third check.

### C2. Probe has `time.sleep(0.1)` after CSS hide

`_data_ready_simple.py` line 169 sleeps 100ms after hiding UI chrome before
capturing. The plan's D5 capture flow doesn't mention this delay. Minor but
could cause intermittent partial-chrome-visible screenshots without it.

### C3. Probe warmup poll interval

The probe polls at 0.2s during warmup (waiting for `needed > 0`), separate
from the 0.5s stability poll interval. The plan's capture flow mentions the
warmup step but doesn't specify the poll interval.
